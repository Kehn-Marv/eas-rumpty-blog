I Built EAS on RumptyCloud. Here's What Actually Happened.

A detailed, honest account of building and deploying the Educational Agentic System on RumptyCloud - the things that worked, the challenges encountered, and the lessons learned.

lemme start from the beginning.

What I was building

I recently embarked on a rather ambitious project for a 30-day sprint hackathon powered by RumptyCloud & Devcenter. The project is EAS, or Educational Agentic System.

EAS is a web-based interactive learning system I am building to help people understand complex concepts beyond conventional, text-heavy explanations.

The idea is simple: a learner should be able to ask a question or explore a difficult concept and receive an adaptive explanation supported by useful visual representations. These can include diagrams, concept maps, step-by-step processes, interactive visualisations and animations.

Rather than giving someone another long block of text and expecting them to figure everything out, I want EAS to make difficult ideas easier to explore, understand and interact with.

There is a lot going on behind the interface, including AI-powered learning workflows, document processing, OCR, retrieval, visualisation generation and an isolated code-execution environment. It is still evolving, but that is the direction I am building towards.

You can explore it here:

  • Live application: https://major-collie-678f34.rumptycloud.app/
  • Source code: https://github.com/Kehn-Marv/eas-web

Why RumptyCloud?

Before EAS, I hadn't spent much time using RumptyCloud.

For this project, I needed somewhere I could run the entire application stack, manage its supporting services, store persistent data and accommodate some fairly demanding processing workloads.

For anyone reading this who is unfamiliar, RumptyCloud is a cloud infrastructure platform for developers. It offers Linux virtual machines, application deployments, managed databases, S3-compatible object storage, persistent volumes, Kubernetes, hosted AI inference and other infrastructure services.

I wanted to document this experience because I think there's value in sharing what using the platform actually felt like, especially as a first-time user.

I'm not writing it to make RumptyCloud look good or bad. I want to be as straightforward as possible about what I experienced: the things I genuinely liked, the challenges I encountered, the mistakes I made on my own side, the workarounds I came up with and the things I would love to see improved.

Some parts were surprisingly smooth. Others were a little more painful than I expected.

Let's get into it.

The things I genuinely loved about RumptyCloud

1. Being able to run the entire application stack

This was easily one of my favourite things.

EAS wasn't designed to be one simple web application.

My Docker Compose setup consists of four services:

  • EAS: The main application, with the Next.js frontend and FastAPI backend running together.
  • Sandbox runner: A separate service for isolated code execution.
  • Redis: Used for internal coordination.
  • PocketBase: Used for authentication and supporting storage.

I initially explored RumptyCloud's standard App Deployments, but its one-port routing model wasn't a natural fit for my existing multi-service setup.

I eventually went with a Linux VM and ran Docker Compose directly on it.

And honestly, I liked that a lot. why tho? if you might ask, its because:

I could run the frontend, backend and supporting services together, configure how they communicated, manage their ports and work with the environment without having to split the application across multiple hosting providers.

The sandbox runner, for example, could remain on the internal Docker network without needing its own public-facing endpoint. The backend could also remain private while the frontend served the public application.

For a project like EAS, that flexibility made a real difference.

I particularly appreciated that I didn't have to redesign the application just to make it fit a more restrictive deployment model.

2. Persistent volumes and keeping important data separate

RumptyCloud's persistent block volumes offered a way to separate important data from the disposable application environment.

The idea is that the application can be rebuilt or replaced while its persistent files remain on the separately attached volume.

This was particularly useful for EAS because some document-processing engines require several gigabytes of model files. I didn't want to download all those models again every time I updated a Docker image.

I configured the application to use persistent cache directories for things such as Docling, Hugging Face, ModelScope and MinerU.

3. Snapshots and the ability to move to a more powerful VM

I initially deployed EAS on the Power plan, which provided 4 GB RAM.

As the application became more demanding, I started noticing resource pressure. At one point, the CPU graph reached 100%.

I eventually moved to the Ultra plan, which provided 8 GB RAM.

One thing I particularly appreciated was the snapshot-based migration path I explored.

Instead of treating the upgrade as a completely fresh installation, I could use the existing VM's boot-disk snapshot as the starting point for another VM, then handle the separate persistent volume independently.

That meant Docker images and other files stored on the boot disk could potentially be preserved through the snapshot, while the application data volume was handled separately.

I found this a much more sensible migration approach than having to repeat every part of the initial setup.

The upgrade to Ultra was useful, although I also learned that more RAM and CPU do not automatically solve every problem. I'll come back to that.

4. Updating the application didn't change the public link

This might seem like a small thing, but it genuinely mattered to me.

I had already shared the EAS website to some of my friends. I didn't want to discover that every time I rebuilt a Docker image or updated the application, the website would get a new URL.

That was one of my initial concerns.

Fortunately, updating the application on the existing VM did not require changing its Rumpty hostname.

I could publish a new image, pull it onto the existing VM, replace the relevant containers and continue using the same public address.

I also appreciated that the previous healthy containers could remain running while the replacement image was downloading. There was no need to take the application offline just because an update had started transferring.

5. Having access to the actual machine

I liked having direct access to the VM through the Rumpty CLI.

There were several occasions when I needed to investigate something beyond what a deployment dashboard could tell me.

I checked running containers, inspected image pulls, examined disk usage, ran commands, checked health endpoints and investigated why certain features were unavailable.

The VM metrics were useful too. They helped me see when the machine was under pressure.

For a project like EAS, where there are several moving pieces, I appreciated having that level of control.

6. Rumpty's stuff 😉

I also liked the fact that RumptyCloud brings several useful infrastructure components into one platform.

VMs, persistent volumes, object storage, managed databases, firewall policies and hosted inference are all useful building blocks.

I didn't necessarily end up using every service for EAS, but having them available made the platform interesting to explore.

Its hosted inference offering was particularly interesting because it exposes an OpenAI-compatible API. That makes it possible to use a familiar client interface for supported chat-completion requests.

I think there is room for RumptyCloud to make its AI capabilities even more useful to developers, particularly those building retrieval-heavy applications. I'll explain what I mean in the feedback section.

The challenges I encountered

Now, this is where things get a little more interesting.

I genuinely enjoyed some parts of using RumptyCloud, but I wouldn't be giving an honest account if I stopped there.

There were a few things that i didnt like, and some things took a considerable amount of time for me to understand.

1. The one-port restriction on standard App Deployments

As I mentioned earlier, my original architecture used Docker Compose with several interconnected services.

RumptyCloud's standard App Deployments route public traffic to one configured port per deployment. That port is also used for the deployment's health checks.

This is an understandable model for many web applications, but it wasn't a natural fit for my existing Compose architecture.

I eventually moved to a Linux VM and managed the services myself.

I don't think every deployment product needs to accommodate every possible application architecture. However, I would appreciate a clearer guide showing when someone should use standard App Deployments and when they should choose a VM.

That distinction would save developers time when deciding how to deploy an application.

2. The default service occupying port 8080 👀

This was one of the first unexpected things I encountered during VM setup.

I had EAS configured to use port 8080, but the application failed to start because the port was already occupied.

After investigating, I discovered that the VM's default Rumpty welcome service was using it.

The issue was resolved by disabling that service:

sudo systemctl disable --now rumpty-welcome.service

Before running that command, I would recommend checking what is actually occupying the port:

sudo ss -tlnp | grep 8080

If it is the default welcome service, disabling it frees up the port for your application.

Heads up: If you're deploying an application that needs port 8080, don't immediately assume your application is broken when you encounter this conflict. Check the port first.

This is something I would love to see made more visible during VM provisioning. It is a small detail that could save developers a surprising amount of debugging.

3. Docker image downloads were painfully slow

This was probably my most frustrating experience throughout the deployment.

The initial EAS image was approximately 4.58 GiB, while the sandbox runner was around 0.32 GiB. Redis and PocketBase were much smaller, at roughly 16 MiB each.

That brought the early estimate for all four images to approximately 4.93 GiB.

And that was just the application images. Parser model files needed to be downloaded separately.

The transfer speed was the real problem.

At one point, the largest image layer was moving at approximately 0.4 MB/s. On later attempts, I saw rates of only a few megabytes per minute.

Some of the downloads continued for hours.

I initially wondered whether the transfer was using my own Wi-Fi or the VM's connection.

It turned out that when the VM pulls an image directly from GitHub Container Registry (GHCR), it is using its own network connection. My home internet connection isn't involved in that transfer.

I even upgraded from Power to Ultra, expecting that the more powerful machine might help.

It didn't automatically solve the problem.

Important lesson: More RAM and CPU didn't necessarily translate into faster downloads. learnt that the hard way 🥲

I couldn't establish from the logs whether the main bottleneck was GHCR, Rumpty's network path, Docker, or an intermittent connection issue. I don't want to assign blame without the measurements to support it.

But from my experience, the transfers were frustratingly slow.

4. A tiny code change

This was another problem that made the image-transfer situation worse.

I made a small change relating to a chat error, but the resulting Docker update involved a layer of approximately 3.77 GB.

Why should a relatively small code change mean transferring such a large layer again?

After reviewing my Dockerfile, I found that I had copied the EAS application source into the dependency-build stage before installing the Python requirements.

This meant changes to the application source could invalidate the cache for the much larger dependency-installation step.

In other words, part of the problem was my own Docker packaging strategy.

I started restructuring the image to make its layers more manageable. One of the changes was to split the installed Python package tree into 64 separate, size-balanced directories, each copied into the final image using its own Docker instruction.

Just so you know: This is a size-balancing strategy, not true content-hash partitioning. It can help prevent one enormous layer from becoming the transfer bottleneck, but it doesn't reduce the total size of a cold image download. Changes to the files can also cause the balancing assignments to shift, so it doesn't guarantee perfect layer-cache reuse.

I still need proper before-and-after measurements to establish how much it improves real deployment times.

I also still need to improve the dependency ordering so that ordinary source-code changes don't unnecessarily invalidate the expensive Python dependency installation.

This was a useful lesson for me: sometimes the slow deployment isn't solely about the hosting provider. How an application is packaged can make a substantial difference.

5. Trying to pull images locally instead

Since direct VM-to-GHCR downloads were proving so slow, I tried another approach.

Rather than asking the Rumpty VM to download the new image, I attempted to pull it through my local Docker connection and transfer the finished image to the VM.

The idea was to use my own internet connection for the registry download, then move the image to the server.

Several smaller layers downloaded successfully, and Docker reused completed layers on subsequent retries.

However, the same large layer repeatedly encountered incomplete-read errors.

The local route didn't become a reliable replacement for the VM's direct pull.

I still think it is a useful alternative to explore when a server-side registry download is painfully slow, but my experience showed that it isn't guaranteed to work all the time.

6. Resource requirements and the Power-to-Ultra upgrade

EAS uses different parsers and processing engines, and not all of them have the same resource requirements.

At one point, the CPU graph reached 100%. I started on Power with 4 GB RAM and later moved to Ultra with 8 GB.

That gave me more room, but it didn't remove the need to plan around the actual workload.

For example, the MinerU 3.x configuration I was using has a published 16 GB minimum RAM for the relevant local-processing setup. My 8 GB Ultra VM was still below that stated baseline.

That does not mean every EAS parser needs 16 GB. It means heavier processing engines need to be considered separately when choosing a plan & I'd also love if the RAMs for the plans were bumped up a little bit or even made to be more flexible / dynamic, in the sense that a user could configure how much they actually needed, dunno if that's a really good idea, but just a suggestion tho.

7. S3-compatible storage and multipart uploads

I also encountered an issue integrating EAS with RumptyCloud's S3-compatible object storage.

When larger uploads went through Boto3's multipart upload path, the operation returned AccessDenied.

The cleanup operation for the incomplete upload also returned AccessDenied.

Smaller uploads using a different path worked.

As a workaround, I changed the relevant upload path to use a single PutObject request.

These are questions I still have are about the actual S3 operations and permissions.

Does the bucket service support the multipart operations Boto3 uses?

Are particular permissions required to initiate, complete or abort multipart uploads?

Is there an automatic cleanup policy for incomplete uploads?

I couldn't establish the cause from the logs available to me, so I don't want to present this as a confirmed S3 compatibility bug.

But clearer documentation here would be extremely useful.

8. PostgreSQL, pgvector and AI application requirements

This is one of the areas I particularly want to highlight because it matters to developers building AI applications.

Many AI applications rely on embeddings, semantic search and retrieval-augmented generation (RAG).

For context, an embedding model converts text into a numerical representation that can be compared with other representations to find semantically related content.

A chat model and an embedding model perform different jobs. Having an inference provider for generating responses doesn't automatically mean that an application also has an embedding provider.

During my EAS deployment, my app expected PostgreSQL's vector extension to be available.

I couldn't establish whether RumptyCloud's managed PostgreSQL service had pgvector installed, whether users could enable it themselves using:

CREATE EXTENSION vector;

or whether the extension needed to be enabled by the platform.

A support for pgvector on RumptyCloud would actually go a really long way

For anyone building AI applications around PostgreSQL, I would strongly recommend confirming extension availability and permissions before committing to a particular database design.

9. The embedding-provider

This is related to the previous point, but it deserves separate attention.

RumptyCloud provides hosted AI inference through an OpenAI-compatible API. It makes the integration familiar for developers already using the OpenAI SDK.

However, the public inference example I found demonstrated chat completions. I couldn't find equally clear information establishing whether the service also supports an embeddings endpoint such as /v1/embeddings, or which embedding models are available.

EAS has a separate embedding-provider configuration, so this is relevant to how I approach knowledge-base indexing and semantic retrieval.

I would love to see a clearer breakdown of the inference operations Rumpty supports, especially whether embedding generation is available alongside chat completions.

Ideally, the documentation would specify the available models, dimensions, batching support, rate limits and pricing.

I don't want to claim that embeddings are unsupported. I simply couldn't confirm the capability from the information I found.

10. A few issues that were actually on my side

Not everything that went wrong during this deployment was a RumptyCloud issue.

Some of the most visible application errors came directly from my own code and packaging decisions.

I just felt it's worth acknowledging because not every error encountered while using a cloud platform is caused by the cloud platform.

The workarounds that helped me

Some of the most useful lessons came from the alternatives I tried when the normal deployment path wasn't working particularly well.

1. Running long deployment commands in the background

The Docker progress output was flooding the interactive terminal and making it difficult to keep the session attached.

I moved the deployment script into a background process and redirected its output to a log file on the VM.

This allowed the pull to continue independently of the browser terminal session. I could then inspect progress and health separately.

It was a simple change, but it made monitoring considerably more manageable.

2. Pulling images locally and transferring them to the VM

I attempted to pull the published image through local Docker and transfer it to the VM.

The goal was to use my local connection instead of relying entirely on the VM's slow registry connection.

This did not become a reliable solution because the large layer repeatedly failed with incomplete reads. However, completed layers were reused on retries, which was useful.

I would still keep this as a possible recovery route, not as a guaranteed deployment method.

3. Applying a targeted code fix without waiting for another full image

One of the more useful workarounds involved a chat-related application error.

Rather than waiting for another multi-gigabyte image transfer, I backed up the existing source file on the VM, copied in the corrected version, checked that it compiled and restarted only the EAS container.

The application subsequently reported healthy.

4. Keeping the existing application online while images downloaded

I was glad the entire application didn't have to go offline just because a new image was being pulled.

The previous containers could remain healthy while the replacement image was transferring.

Only when the image was available did I proceed with replacing the running containers.

Where I think RumptyCloud could improve

I don't think feedback should stop at listing frustrations. I'd rather explain what would make the experience better for the next developer.

1. Better image-pull visibility and performance

This is my biggest request.

Large Docker images can make first-time deployments and subsequent updates take hours.

Better registry connectivity, regional image caching, resumable transfers and more detailed layer-level progress would make a meaningful difference.

I'd particularly appreciate being able to see:

  • The image digest being pulled.
  • The current layer being transferred.
  • Bytes downloaded and remaining.
  • Transfer rate.
  • Retry count.
  • The latest error, if a transfer fails.

When a pull is taking several hours, knowing whether it's progressing, retrying or genuinely stuck is important.

I also recognise that image size and layer caching are partly the developer's responsibility. Still, better visibility from the platform would make it much easier to distinguish application packaging issues from network or registry issues.

2. A clearer multi-service Docker Compose deployment guide

I would love a practical, end-to-end guide for developers who want to run Docker Compose on a Rumpty VM.

It should cover:

  • Internal service networking.
  • Public versus private ports.
  • Reverse proxies.
  • Firewall configuration.
  • Persistent volume mounting.
  • Deployment and image updates.
  • Health checks.
  • Recovery and rollback.

Rumpty's VM deployment documentation currently explains deployment workflows involving GitHub Actions and file transfer, but I couldn't find an equally direct guide for the GHCR-based Docker Compose workflow I used.

A specific example would make this easier to navigate.

3. More detailed S3 multipart upload documentation

The S3-compatible bucket integration is useful, but I'd appreciate an explicit compatibility and permissions reference.

I still had these particular questions in mind:

  • Does the service support multipart initiation, part upload, completion and abort?
  • What permissions must an access key have for each?
  • Are incomplete multipart uploads automatically cleaned up?
  • Is there a configurable lifecycle policy?
  • Are there request or object-size limitations?

This would help developers avoid guessing when an upload fails.

4. A PostgreSQL extension compatibility list

For managed PostgreSQL, a public list of available extensions would be extremely useful.

I would particularly like to know whether pgvector is available, which PostgreSQL versions support it, and whether users can enable it themselves.

For AI developers building RAG applications, this is an important database-planning detail.

5. Clearer AI inference and embedding documentation

I'd love to see the hosted inference documentation list its supported API operations and available models more explicitly.

Chat completions and embedding generation are different capabilities. Developers building RAG applications need to know whether both are supported.

A dedicated embeddings section would be a useful addition.

6. More guidance for resource-intensive workloads

Applications involving OCR, local model execution, document parsing and rendering have different compute and memory requirements.

Guidance on sizing VMs for these workloads, monitoring resource consumption and managing concurrency would help developers make better infrastructure decisions.

7. Make first-boot information more visible

The port 8080 welcome-service conflict is a good example of something that could be more visible during VM setup.

A short notice explaining that a default service may already occupy the port would prevent unnecessary debugging.

8. Clearer backup and recovery expectations

Another thing I noticed while reviewing the managed database documentation was that automatic database backups, point-in-time recovery and a managed restore flow are not currently available.

The documentation recommends taking manual backups using tools such as pg_dump.

This absence didn't cause any EAS incident or bugs tho. But it is important information for anyone considering the managed PostgreSQL service for valuable production data.

I'd appreciate making backup expectations particularly prominent during database setup, and eventually offering scheduled backups and a more convenient restoration process.

A few things this experience taught me

I learned that getting an application online is only one part of deploying it. Understanding Docker images, persistent storage, resource requirements, network performance and proper deployment verification is just as important.

I also learned to distinguish between platform limitations and problems caused by my own implementation, rather than immediately blaming one for the other.

So, would I use RumptyCloud again?

Yes. Absolutely.

Despite the frustrating parts, RumptyCloud gave me the infrastructure flexibility I needed to run EAS without fundamentally changing its architecture.

Being able to use a Linux VM, manage my entire Docker Compose stack, attach persistent volumes, inspect resources and update the application on the existing machine were all genuinely valuable.

The biggest challenge was getting large images transferred and making the deployment process repeatable.

Some of that friction came from my own packaging decisions. Other things, particularly the multipart-upload errors and the questions around database extensions and embeddings, are areas where I'd love to see clearer answers from the Rumpty team. I'm sure other developers interested in building and deploying on the platform would appreciate that clarity too.

Overall, I'd rate my experience with RumptyCloud an 80/100, based on my first experience with the platform and everything I've encountered so far.

I'm usually one to keep a good find to myself, but honestly, I don't think I'm doing that this time. I'm more than happy to introduce as many of my developer friends and people in my network to Rumpty as possible. It's too good a find to keep to myself!

It's simply my own way of showing support and saying thank you to the developers for building something I genuinely enjoyed using.

A massive kudos to the entire RumptyCloud dev team! 🫡

I genuinely can't wait to see where this platform goes over the next few years. There's so much potential here, and I'm looking forward to seeing what comes next.
